# Stage 1 — Scanning Third-Party Skills, MCP Servers, and Plugins for Malicious Content

New topic, flagged 2026-08-23 in `topic-index.md`, distinct from the general verification *practice* already covered in `security-and-supply-chain.md` (checklist, 2026 incidents — ClawHub poisoning, Snyk's ToxicSkills study, OWASP Agentic Skills Top 10, Socket.dev for dependency monitoring). That doc is not re-covered here. This doc answers the one concrete gap it leaves open: what actual tool or repeatable process scans a *specific* skill, MCP server, or plugin for malicious content before you adopt it.

## 1. This category went from thin to crowded in 2026

Between roughly March and August 2026, purpose-built scanners for this exact problem went from nonexistent to plentiful — but the harder problem shifted from "is there a tool" to "do these tools actually agree with each other" (§4 below is the important section).

- **NVIDIA `SkillSpector`** (`github.com/NVIDIA/SkillSpector`, 14.4k★/1.2k forks, Apache-2.0) — scans a local dir, single `SKILL.md`, zip, or GitHub URL directly, so it works pre-install. Two-pass: static (regex + Python AST + taint-tracking + live OSV.dev dependency lookups, 68 patterns/17 categories) plus an optional LLM semantic pass (~87% claimed precision). Outputs a 0–100 risk score; SARIF/JSON/markdown output; can run *as* an MCP server exposing a `scan_skill()` tool for gating installs at runtime. Launched ~2026-08-03 — new but promising, corporate-backed rather than a weekend project.
- **Snyk `agent-scan`** (`github.com/snyk/agent-scan`, 2.9k★/260 forks, Apache-2.0, actively shipping — v0.6.0 released 2026-08-19) — the only mature tool covering **both** skills and MCP servers in one pass, descended from Invariant Labs' MCP security research. Risk-scores 15 categories including prompt injection, tool poisoning, tool shadowing, toxic flows. Also available with zero install as a browser drag-and-drop tool (`labs.snyk.io/experiments/skill-scan`); Snyk reports finding issues across "nearly 4,000 agent skills across major marketplaces" via this tool.
- **Cisco AI Defense `skill-scanner`** (2.2k★/261 forks, Apache-2.0, YARA + YAML rules + LLM pass) — honest about its own limits: "no findings ≠ no risk." No MCP coverage claimed.
- **Sentry's `skill-scanner`** — a Skill that scans Skills, bundled in `getsentry/skills` (~930–945★, real company backing). Checks permissions requested vs. actually used, in addition to the usual injection/exfiltration/secret categories.
- **`NMitchem/SkillScan`** — the most technically interesting design (a three-stage audit/predict/test pipeline that actually runs the skill in a sandboxed microVM against honeypot canary credentials) but **5 stars, 1 fork — effectively a one-person project.** Worth reading for the canary-file sandboxing technique, not worth depending on.

## 2. MCP-specific: rug-pull/drift detection is the real gap, and only one tool addresses it

`mcp-model-context-protocol.md` §4 already names the "rug pull" risk — a tool's description changing after you've approved it, with no new consent prompt. One project addresses this directly: **`DataScience-EngineeringExperts/mcp-warden`** canonicalizes an MCP server's declared tool/resource/prompt surface (RFC 8785 JSON canonicalization + SHA-256), pins it to a lock file, and fails CI on drift, classifying the type of change rather than treating all changes alike. **2 stars, 0 forks — a one-person project**, but with unusually good supply-chain hygiene for its size (Sigstore-signed releases, OIDC trusted publishing). The technique — hash the tool surface, alert on change — is more valuable than the specific tool; it's roughly 30 lines to reimplement. Snyk's `agent-scan` does *not* do drift detection as far as this pass could determine (its docs describe static scanning only, not pinning/whitelisting).

## 3. What Anthropic itself offers — directly answers the "is there a built-in option" question

**Automatic skill/plugin scanning exists but is Enterprise-plan-only** (`support.claude.com/en/articles/15927065`, confirmed directly): runs automatically on upload/edit in Enterprise plans across Claude, Claude Cowork, and Enterprise marketplaces; 1–2 minutes, pass/warn/fail. No individual/Pro/Max availability, and no documented way to trigger a manual scan of an arbitrary skill even on Enterprise.

Two things individuals *do* get, per `code.claude.com/docs/en/discover-plugins`: the **community marketplace** (`anthropics/claude-plugins-community`) runs automated validation/safety screening and SHA-pins each plugin to a specific commit — a meaningful trust tier above an arbitrary GitHub repo, though Anthropic's own docs still disclaim "can't verify that they work as intended." And the `/plugin` Discover tab shows a **"Will install"** pane before you commit — every command, agent, skill, hook, MCP server, and LSP server a plugin adds, plus a context-cost estimate — a free, zero-tool review step worth making a habit of.

## 4. The critical caveat — read this before trusting any scan result

This is the finding that should shape how any of the above gets used, not a footnote:

- **Scanners barely agree with each other.** Ilya Kabanov (`theweatherreport.ai`, 2026-03-24) ran seven scanners (including VirusTotal, Snyk, Socket, Cisco) across 238,180 unique skills. On the one marketplace where five scanners overlapped, they agreed on **33 of 27,111 skills — 0.12%**. Of skills flagged by at least one scanner, ~72% were flagged by exactly one.
- **Static scanning is straightforwardly evadable.** HKUST researchers (arXiv 2607.02357, July 2026) built `SkillCloak`: payload-packing bypassed scanners >90% of the time, and semantics-preserving code rewriting cleared >80% of static scanners and 96% against hybrid static+LLM tools — "the best static scanner... fell from about 99% to roughly 10% the moment the rewriting trick came into play." Their sandbox-based counterpart, `SkillDetonate`, caught 97% of synthetic and 87% of real-world malicious skills — the sandbox approach meaningfully outperforms static scanning, at a real time cost (~2.5 min/skill).
- **Scanners also massively over-flag without context.** IT:U Linz/University of Vienna researchers (arXiv 2603.16572) found marketplace scanners classify up to 46.8% of skills as malicious in isolation, but only 0.52% remain suspicious once evaluated against the skill's own GitHub repository context (age, commit history, stars, whether the code plausibly matches the stated purpose) — a roughly 90x reduction.

**The synthesis**: a clean scan proves very little on its own; a dirty scan proves less than it looks like it does; the signal that actually discriminates is repository-provenance context plus sandboxed behavioral testing, not static pattern-matching alone.

## 5. Manual process, if not running a tool

Aryaman Behera (Repello AI, 2026-02-24) gives a grep-level-specific four-step read, not the general checklist already in `security-and-supply-chain.md`: read the manifest end to end flagging any reference to environment variables or credential-shaped names; inventory every shipped file (a skill with no stated need for code shouldn't ship scripts/binaries); hunt for obfuscation (base64 blobs, mixed-language text, hidden Unicode); enumerate every outbound network reference against what the skill claims to talk to. He names "conditional activation" (a payload that only triggers under specific conditions — a sleeping payload) as the pattern static reads miss entirely, which is exactly what SkillScan's sandbox stage and SkillDetonate above are built to catch. For an MCP server specifically, the practical version of `mcp-warden`'s technique is: hash the declared tool surface once, re-check it before each session, and treat *any* change to a tool description as a re-approval event.

## 6. Practical read for a solo setup

None of the scanners above should be trusted as a pass/fail gate on their own, per §4 — but running one (SkillSpector or `agent-scan`'s zero-install web version are the lowest-friction options) as one more signal alongside `security-and-supply-chain.md`'s existing checklist (checkable author identity, reading the manifest yourself, preferring Anthropic-vetted sources) is still worth the five minutes it costs, precisely because static scanning's blind spots and false positives point in different directions from a manual read. The Anthropic community marketplace's SHA-pinning (§3) is arguably the single highest-leverage move available today, since it moves the trust decision from "did I audit this" to "did Anthropic's screening + provenance pinning already do the boring 90%."
