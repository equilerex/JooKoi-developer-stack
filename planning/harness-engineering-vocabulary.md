# Stage 1 — Harness Engineering, Agent Loops, Context Engineering, Repository Legibility

New topic (not covered by any prior stage-1 doc), surfaced via a ChatGPT-sourced breakdown (quarantine trail resolved and removed once processed). The source names four things as if separate; the primary sources treat them as layers of one system — the harness is the outer container, agent loops are what runs inside it, context engineering is how information flows through it, and repository legibility is what makes the surrounding codebase usable by it. Covered together here for that reason. No pick — practices to consider adopting, not a mandate.

## 1. Harness engineering — what it actually means

Per OpenAI's own framing (`openai.com/index/harness-engineering/` — confirmed real via independent secondary coverage; the page itself blocks direct fetching but three independent write-ups, including InfoQ and Milvus's technical blog, converge on the same content): a harness is the designed environment around an agent — the primary engineering job shifts from writing code to "designing environments, specifying intent, and building feedback loops." OpenAI's own worked example: over one million lines of a real product generated with zero manually-written code, by (a) making the repository structurally legible to agents, (b) encoding the project's core principles/conventions directly into the repo, and (c) running scheduled background agent tasks that scan for convention deviations and submit their own refactoring PRs.

The dump's list of what a harness covers — tool access, permissions/sandboxing, context loading, planning/task state, retries/recovery, test execution, verification, subagents, compaction/memory, logging, stop conditions — is a reasonable inventory, but it's worth being precise about the *level*: this project already has real harness components without naming them as such. `AGENTS.md` files are context loading. `TODO-LIST.md` and `llm-progress-complete.jsonl` are task state and logging. The Superpowers skill framework already active in this Claude Code session is a planning/verification layer. None of that changes by naming it "harness engineering" — the value of the term is that it names the *whole system* as one design surface, so a change to one part (e.g. adding a new skill) gets evaluated against how it affects the others (context budget, verification coverage) rather than in isolation.

## 2. Agent loops — a correction worth making

The dump attributes "the agent loop as a core runtime capability" to Anthropic's `effective-harnesses-for-long-running-agents` article. Direct fetch of that article shows this is **not** what it argues — the piece explicitly states plain looping is insufficient: "compaction isn't sufficient. Out of the box, even a frontier coding model like Opus 4.5 running on the Claude Agent SDK in a loop across multiple context windows will fall short." Its actual proposal is a **two-agent harness**: an Initializer Agent (first session, sets up scaffolding) and a Coding Agent (subsequent sessions, makes incremental progress against externalized state), where the state that survives between fresh context windows lives in plain files — a `claude-progress.txt`, git commit history, and a JSON feature-completion list — not in the model's memory or an automatic compaction summary. The stated reason plain loops fail in practice isn't infrastructure, it's a specific model behavior: Claude tends to "attempt to one-shot the app" and prematurely declare completion, which is why the harness needs an explicit, externally-checkable definition of done rather than trusting the loop to self-report.

This is directly actionable and cheap: the general shape (external progress file + explicit completion criteria the agent can't talk its way past) is exactly what this repo's own `TODO-LIST.md`/`llm-progress-complete.jsonl` pattern already does at the project level, and what `planning/decisions/001-first-design-skill-picks.md` does at the single-decision level. Worth reinforcing explicitly rather than treating as a separate new thing to adopt: the practice is already here, the terminology is what's new.

## 3. Context engineering — real gap or already covered?

Checked against [`session-and-token-economics.md`](./session-and-token-economics.md) directly. That doc covers cost/economics of context (caching pricing, linear cost growth, compaction-vs-fresh tradeoffs) — a financial/mechanical framing. Anthropic's `effective-context-engineering-for-ai-agents` article (fetched directly) defines a **different, complementary** discipline: "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference," with the guiding principle of finding "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." This is about *what* goes in the window, not what it costs once it's there.

Concrete practices from the source, genuinely not covered in the existing session-economics doc:
- **Minimal, non-overlapping tool sets** that return token-efficient information — tool bloat and ambiguous tool overlap actively confuses the model, independent of any cost concern.
- **"Just-in-time" context** — agents dynamically retrieve data via tools at the moment it's needed (file paths, stored queries, links as lightweight identifiers) rather than front-loading everything into the system prompt. This is the same principle Agent Skills' progressive disclosure already implements at the skill level (already covered in [`skill-libraries-and-marketplaces.md`](./skill-libraries-and-marketplaces.md)) — worth noting the pattern repeats at the tool-design level too, not just the skill-library level.
- **Structured note-taking as persistent external memory** — distinct from compaction (compaction summarizes what happened; note-taking is the agent deliberately writing durable facts to a file as it works, meant to be read back later). This is close to, but not identical to, the Topic #10 memory-ledger question — worth cross-referencing when that pick is made.
- **Diverse canonical examples over exhaustive edge-case lists** — a prompt-writing guideline, applies directly to how skills and `AGENTS.md` files should be written.

Net: real, complementary gap. Session-economics answers "does this cost too much and is quality degrading"; context engineering answers "is the right information in the window at all, and is there too much irrelevant material crowding it." Both matter; neither substitutes for the other.

## 4. Repository legibility

Named explicitly in OpenAI's harness-engineering piece as one of the three pillars of their million-line experiment: a structured repository, with the project's conventions encoded directly into it (not left as tribal knowledge), so an agent starting fresh can discover what it needs from the repo itself rather than from a person's memory or a Slack thread. The dump's list — architecture notes, decision records, explicit test commands, known-failure documentation, generated codebase maps, schemas, executable validation, small coherent files — maps almost one-to-one onto conventions this repo and the JooKoi product repo already commit to: `JooKoi-frontpage-to-the-open-web/AGENTS.md` states "Decisions are ADR-lite... one file per decision," names `architecture.md` as the whole-system doc (deferred to Stage 5, not built yet — a legibility gap by its own admission, not an oversight), and separates `sources/` (human-authored) from `data/` (machine-observed) explicitly so an agent can tell which clock governs which files without being told in conversation.

The one thing genuinely worth adding to this repo's own practice, not already covered: **executable checks as part of the system of record**, not just written docs. OpenAI's background-agent pattern (scheduled tasks scanning for convention deviations, submitting their own fixes) is a step beyond what's here — this repo's conventions are currently enforced by whoever reads `AGENTS.md` before acting, not by anything that runs and checks. Given this repo's own stated anti-speculative-infrastructure stance (`docs/reasoning.md`), building a scheduled deviation-scanner now would be premature — there isn't enough accumulated convention yet to make automated drift-checking worth the setup cost. Worth naming as a real future step once `skills/`/`prompts/` have real content, not something to build today.
