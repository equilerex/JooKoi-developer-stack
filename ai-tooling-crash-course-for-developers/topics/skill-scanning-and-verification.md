# Stage 1 — Scanning Third-Party Skills, MCP Servers, and Plugins for Malicious Content

People share ready-made add-ons for AI coding tools, similar to browser extensions or phone apps made by strangers — most are fine, but some have been found to secretly steal passwords, copy private files, or send information somewhere it shouldn't go. Scanning is the practice of checking one of these add-ons for hidden bad behavior before you install and trust it with access to your computer. Worth knowing about if you install add-ons for an AI coding tool that other people wrote; skip it if you never install anything beyond what came built in.

New topic, flagged 2026-08-23 in `topic-index.md`, distinct from the general verification *practice* already covered in `security-and-supply-chain.md` (checklist, 2026 incidents — ClawHub poisoning, Snyk's ToxicSkills study, OWASP Agentic Skills Top 10, Socket.dev for dependency monitoring). That doc is not re-covered here.

**The conclusion this document builds toward:** a scanner is better than no scanner, but no single scanner is sufficient evidence that a third-party agent artifact is safe. Everything below exists to justify that line, not to talk you out of scanning.

## 1. What you're actually defending against

Before looking at any scanning product, it helps to know what the malicious content in a skill, MCP server, or plugin actually looks like. These are the patterns documented in real incidents and research as of 2026 — not hypothetical attack classes.

**Direct malicious instructions embedded in the artifact.** The simplest case: a `SKILL.md` or manifest just tells the agent to do something harmful, in plain language. This is the bulk of what's been found in the ClawHub poisoning campaigns — see `security-and-supply-chain.md` for the incident numbers (341–1,184 malicious skills depending on which count, [Snyk's ToxicSkills study](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/) finding 1,467 of 3,984 scanned skills with at least one flaw).

**Indirect prompt injection.** The malicious instruction doesn't live in the artifact you installed — it lives in content the artifact later reads (a webpage, an email, a file, a tool response), and the agent treats as instructions rather than data. [Unit 42's documented case](https://unit42.paloaltonetworks.com/ai-agent-prompt-injection/) found a real webpage (advertising counterfeit military-style glasses) with hidden prompts designed to trick an AI-based ad-review agent into approving content it should have rejected — the first reported real-world case targeting this kind of system, per the researchers. The mechanism generalizes to any agent that reads untrusted content and can act on what it reads.

**Obfuscated or encoded content.** [SlowMist's analysis of the ClawHub poisoning](https://slowmist.medium.com/threat-intelligence-analysis-of-clawhub-malicious-skills-poisoning-0448ffd49c80) found attackers Base64-encoding payloads directly inside `SKILL.md` files, with a two-stage loader that decodes and runs the hidden stage only at execution time — invisible to a plain-text read of the file.

**Dynamically constructed URLs or commands.** Rather than shipping a hardcoded malicious endpoint (which a scanner can pattern-match), the artifact builds a URL or command at runtime — e.g., appending stolen environment-variable values as query parameters to an otherwise innocuous-looking request. Anthropic's own guidance names this directly: a malicious Skill can be written to read environment variables and exfiltrate them "via URL parameters or embedded requests" ([Anthropic Help Center](https://support.claude.com/en/articles/15927065-get-started-with-skill-and-plugin-scanning)).

**Instructions that look innocuous to a human but read differently to an LLM.** A dedicated study of malicious skills found in the wild — ["Do Not Mention This to the User": Detecting and Understanding Malicious Agent Skills in the Wild](https://arxiv.org/pdf/2602.06547) — documents a dual-instruction pattern: the human-facing description of a skill reads as legitimate, while a separate embedded directive (its title example: literally "do not mention this to the user") tells the model to take an action and hide it from the person who installed the skill. A manual read that only checks "does the stated purpose sound reasonable" misses this by design.

**Delayed or conditional malicious behavior.** A payload that only activates under specific conditions — a particular file present, a particular date, a particular user action — so it passes both a static read and a one-off test run. Repello AI's manual-audit writeup names this "conditional activation" as the pattern static reads consistently miss (see §5 in the earlier draft's sourcing, still applicable here). It's also the exact gap that behavioral/sandbox testing is built to catch rather than pattern-matching (§4 below).

**Malicious scripts or resources bundled with and executed by a skill.** [Reversec's "Skill Issues" writeup](https://labs.reversec.com/posts/2026/05/skill-issues-compromising-claude-code-with-malicious-skills-agents-part-1) demonstrates a Claude Code skill whose frontmatter grants broad tool permissions (`allowed-tools: Bash(*)`) combined with inline command execution, letting a bundled reverse-shell command run without the confirmation prompt a user would normally see for shell access. The risk isn't only in the natural-language instructions — it's in whatever scripts or binaries ship alongside them and what permissions the artifact grants itself to run them.

**Malicious MCP server or plugin behavior.** [The `postmark-mcp` incident](https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html) is the clearest documented case: a package impersonating the real Postmark MCP server ran cleanly and matched the legitimate repo for 15 versions, then version 1.0.16 added a single hidden line that BCC'd every outgoing email to an attacker-controlled address — silently forwarding an estimated 3,000–15,000 emails a day for over a week before removal. Nothing about the malicious version looked different at a glance; the change was one line, deep in the diff, activated with full pre-granted permissions.

**Attempts to exfiltrate credentials, source code, environment variables, or other accessible data.** The consistent end goal across most of the above: API keys, `.npmrc`/CI tokens, source code, or local files sent somewhere the user didn't intend. The [keyv/cacheable npm worm](https://www.wiz.io/blog/keyv-and-cacheable-npm-supply-chain-attack) (not agent-specific, but the same failure mode reaching agent tooling) targeted `.npmrc` tokens, GitHub CLI tokens, AWS credentials, and Kubernetes configs specifically. In the agent-artifact context, the same exfiltration goal shows up as "read this environment variable and put it in a URL" (Anthropic's own example above) or "read this file and describe its contents in a way that gets sent to an external service."

## 2. The defense stack, in order

Given all of the above, no single layer is sufficient on its own. Treat these as a stack, applied roughly in this order:

1. **Inspect the source yourself.** Read the manifest/`SKILL.md` end to end. Inventory every bundled file — a skill with no stated need for code shouldn't ship scripts or binaries. Look specifically for the patterns in §1: encoded blobs, dynamically built URLs, references to environment variables or credential-shaped names, and instructions that contradict or extend beyond the artifact's stated purpose.
2. **Use scanners — plural.** A single scanner is one static or semi-static pass with known blind spots (§4). Running more than one, from different vendors with different detection approaches, catches more than any one alone.
3. **Compare signals where practical, since tools disagree with each other.** Don't take a clean result from one scanner as final — cross-check it against another tool's output, the repo's own history/context, or a manual read, precisely because independent testing shows scanners frequently disagree (§4).
4. **Restrict the permissions granted to the artifact.** Don't grant broad tool/shell/network access by default — grant only what the stated purpose actually requires and treat any request for more as a red flag in its own right (this is what the "Reversec" example in §1 exploited).
5. **Sandbox execution where possible.** Running unfamiliar code in an isolated environment before trusting it with real credentials or your real filesystem is the single highest-leverage step available and the one most often skipped for convenience. See `agent-sandboxing.md` for how to actually do this — not repeated here.
6. **Prefer reputable, actively maintained sources.** A repo's popularity and age aren't proof of safety on their own (`security-and-supply-chain.md` covers why — compromised-legitimate-package incidents), but a first-party or well-established maintainer with a real history is still a meaningfully better starting point than an anonymous, week-old account.
7. **Treat scanner output as one piece of evidence, not a guarantee.** This is the conclusion, not a footnote — see §4 and the top of this document.

## 3. Scanner landscape (as of August 2026)

Purpose-built scanners for this exact problem went from nonexistent to plentiful over 2026:

- **NVIDIA `SkillSpector`** ([`github.com/NVIDIA/SkillSpector`](https://github.com/NVIDIA/SkillSpector), Apache-2.0) — scans a local dir, single `SKILL.md`, zip, or GitHub URL directly, so it works pre-install. Two-pass: static (regex + Python AST + taint-tracking + live OSV.dev dependency lookups) plus an optional LLM semantic pass. Outputs a 0–100 risk score; SARIF/JSON/markdown output; can run *as* an MCP server exposing a `scan_skill()` tool for gating installs at runtime.
- **Snyk `agent-scan`** ([`github.com/snyk/agent-scan`](https://github.com/snyk/agent-scan), Apache-2.0) — covers both skills and MCP servers in one pass, descended from Invariant Labs' MCP security research. Risk-scores categories including prompt injection, tool poisoning, tool shadowing, and toxic flows. Also, available with zero installation as a browser drag-and-drop tool ([`labs.snyk.io/experiments/skill-scan`](https://labs.snyk.io/experiments/skill-scan)).
- **Cisco AI Defense `skill-scanner`** ([`github.com/cisco-ai-defense/skill-scanner`](https://github.com/cisco-ai-defense/skill-scanner), YARA + YAML rules + LLM pass) — honest about its own limits in its own docs: "no findings ≠ no risk." No MCP coverage claimed.
- **Sentry's `skill-scanner`** — a Skill that scans Skills, bundled in [`getsentry/skills`](https://github.com/getsentry/skills). Checks permissions requested vs. actually used, in addition to the usual injection/exfiltration/secret categories.
- **`NMitchem/SkillScan`** — the most technically interesting design (a three-stage audit/predict/test pipeline that actually runs the skill in a sandboxed microVM against honeypot canary credentials), but a very small, effectively one-person project. Worth reading for the canary-file sandboxing technique, not worth depending on it alone.

**MCP-specific drift/rug-pull detection is a separate, narrower gap.** A tool's declared behavior can change silently after you've already approved it — the "rug pull" pattern. [`DataScience-EngineeringExperts/mcp-warden`](https://github.com/DataScience-EngineeringExperts/mcp-warden) canonicalizes an MCP server's declared tool/resource/prompt surface and pins it to a lock file, failing on drift. It's a small project, but the underlying technique — hash the declared tool surface once, alert on any change — is simple enough to reimplement directly.

**What Anthropic itself offers.** Automatic skill/plugin scanning exists but is Enterprise-plan-only ([Anthropic Help Center](https://support.claude.com/en/articles/15927065-get-started-with-skill-and-plugin-scanning), confirmed directly): it runs automatically on upload/edit across Claude, Claude Cowork, and Enterprise marketplaces, with a pass/warn/fail result in 1–2 minutes. There's no individual/Pro/Max equivalent and no documented way to trigger a manual scan of an arbitrary skill even on Enterprise. What individuals *do* get: the community marketplace (`anthropics/claude-plugins-community`) runs automated validation/safety screening and SHA-pins each plugin to a specific commit, and the `/plugin` Discover tab shows a "Will install" pane before you commit to anything — every command, agent, skill, hook, MCP server, and LSP server a plugin adds. Anthropic's own docs still disclaim they "can't verify that they work as intended" even for the vetted marketplace.

## 4. Why no single scanner is enough — the evidence

This is the section that shapes how everything above should actually be used.

- **Scanners barely agree with each other.** [Ilya Kabanov's independent study](https://theweatherreport.ai/posts/skill-scanner-disagreement/) (2026-03-24) ran seven scanners (including VirusTotal, Snyk, Socket, Cisco) across 238,180 unique skills. On the one marketplace where five scanners' coverage overlapped, they agreed on only 33 of 27,111 skills — 0.12%. Of skills flagged by at least one scanner, 72% were flagged by exactly one.
- **Static scanning is straightforwardly evadable.** HKUST researchers ([arXiv 2607.02357](https://arxiv.org/abs/2607.02357), July 2026) built `SkillCloak`: across eight scanners and 1,613 in-the-wild malicious skills, a packing technique bypassed every scanner more than 90% of the time, and a semantics-preserving rewriting technique cleared over 80% of static scanners and 96% of a hybrid static+LLM scanner. Their behavior-based counterpart, `SkillDetonate`, caught 97% of injected payloads in testing, holding up across original, obfuscated, and packed forms — the sandbox/behavioral approach meaningfully outperforms static scanning, at a real time cost.
- **Scanners also over-flag heavily without context.** Researchers from TU Wien and collaborators ([arXiv 2603.16572](https://arxiv.org/abs/2603.16572)) found marketplace scanners classify up to 46.8% of skills as malicious when evaluated in isolation, but only 0.52% remain suspicious once cross-checked against the skill's own GitHub repository context (age, commit history, stars, whether the code plausibly matches the stated purpose) — roughly a 99% reduction in flagged skills.

**The synthesis**: a clean scan proves very little on its own; a dirty scan (from marketplace-level automated screening) proves less than it looks like it does without repo context; the signal that actually discriminates well is repository-provenance context plus sandboxed behavioral testing, not static pattern-matching alone. None of this means scanning is worthless — it means a scan result is one input into a judgment call, not the judgment call itself.

## 5. Does the current MCP spec close any of this?

Checked directly against the [official Model Context Protocol specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) and the [2026-07-28 release candidate notes](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), rather than assumed from memory:

- **Tool annotations exist, but the spec itself tells clients not to trust them.** Tools can carry optional `annotations` describing behavior (e.g., destructive, read-only, idempotent). The spec is explicit: "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers" — the mechanism exists, but it's advisory metadata a malicious server can simply lie about, not a verified property.
- **Human-in-the-loop consent is a "SHOULD", not an enforced requirement.** The spec recommends implementations "SHOULD" prompt for user confirmation on sensitive operations and show tool inputs before calling the server — this is guidance for client implementers, not a protocol-enforced guarantee every client honors.
- **No tool-definition signing or integrity verification is part of the base spec.** There is no cryptographic hash, version binding, or signature tying a tool's definition to what a user previously approved — meaning the "rug pull" pattern (a server changing a tool's behavior or description after approval, with no re-consent prompt) is not addressed by the current specification. Proposals to fix this (e.g., the [Enhanced Tool Definition Interface / ETDI](https://arxiv.org/pdf/2506.01333), which binds tool definitions to signed JWTs) exist in research but are not part of the adopted spec.
- **The 2026-07-28 RC's security-relevant changes are about authorization and audit, not artifact trust.** It hardens OAuth/OIDC authorization flows (mix-up-attack mitigation per RFC 9207) and constrains when a server can send unsolicited requests to a client, plus sandboxes any UI a server ships inside an iframe with the same consent path as a direct tool call. None of these change whether a given tool's declared behavior can be trusted or verified against tampering.

**Bottom line**: the current spec gives you a defined consent hook and an explicit "don't trust annotations blindly" rule, which is more than earlier versions had — but it does not provide signing, drift detection, or any built-in way to verify a tool hasn't changed since you approved it. `mcp-warden`'s hash-and-pin approach (§3) remains a client-side workaround, not something the protocol does for you.
